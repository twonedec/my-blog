개인 NAS(Network Attached Storage) 환경에서 Claude API를 연동하여 보유 종목의 주요 이슈를 매일 아침 카카오톡 리포트로 받아볼 수 있는 자동화 파이프라인을 구축했습니다. 본 포스팅에서는 시스템의 전체적인 아키텍처를 공유하고, 초기 설계 과정에서 간과하기 쉬운 비용 리스크와 API 한도 설정 등 시행착오를 통해 얻은 기술적 교훈들을 정리합니다.

## 1. 시스템 아키텍처 및 운영 환경

본 자동화 프로그램은 데이터 수집부터 최종 엔드포인트 발송까지 총 6단계의 독립된 모듈로 분리되어 유기적으로 동작합니다.

### 6단계 데이터 파이프라인 구성

- 단계 1: 뉴스 데이터 수집 (`collector.py`)
- 단계 2: 중복 콘텐츠 필터링 및 정제 (`deduper.py`)
- 단계 3: DART 기업 공시 수집 (`dart_collector.py`)
- 단계 4: LLM 기반 호재 및 악재 판단 Engine (`engine.py`)
- 단계 5: 기술 지표 기반 시장 스크리닝 (`recommender.py`)
- 단계 6: 카카오 비즈메시지 API 연동 및 발송 (`reporter.py`)

### 인프라 및 실행 환경

- **하드웨어 자원:** Synology DS423+ NAS (24시간 상시 가동 환경 활용)
- **컨테이너 및 스케줄러:** Docker 가상화 환경 위에 cron을 배치하여 평일 오전 8시 정각에 태스크 자동 스케줄링
- **최종 알림 인터페이스:** 카카오 비즈니스 메시지 API를 연동하여 개인 카카오톡으로 다이렉트 전송

---

## 2. 프로젝트 개발 동기

장 시작 전 제한된 시간 내에 개인이 포트폴리오 내 10개에서 20개 사이의 종목들을 대상으로 모든 신규 뉴스를 모니터링하는 것은 정량적으로 불가능에 가깝습니다.

기존 포털 금융 앱의 경우 단순 타임라인 형태로 정보가 나열되기 때문에, 각 기사의 텍스트를 읽고 실제 주가에 미칠 영향(정성적 가치 판단)을 분석하는 데 많은 리소스가 소모됩니다. 특히 출근 시간 등 바쁜 시점에 제목만 스캔하다가 리스크가 큰 악재 공시를 놓치는 오버사이트가 발생하기도 했습니다.

이 문제를 해결하기 위해 LLM(대형 언어 모델) API의 정성적 분석 능력을 활용하여 뉴스 데이터의 센티먼트(호재/악재)를 자동 판별하고 결과만 요약 수신하는 파이프라인을 기획하게 되었습니다.

## 3. 초기 설계 시 주의해야 할 3가지 엔지니어링 실책

프로젝트 초기 단계에서 아키텍처 설계를 면밀히 하지 못해 직면했던 정량적 문제점들입니다. 시스템 구축 전 반드시 체크해야 할 리스크 요인입니다.

### 첫 번째 리스크: 단일 LLM 배치로 인한 API 런타임 비용 폭탄

초기 프로토타입 버전에서는 텍스트 분석, 전 종목 스크리닝, 최종 데이터 가공 등 모든 연산 과정을 고성능 모델인 Claude Sonnet 단일 API 엔진으로 처리했습니다. 이 경우 3,000개가 넘는 상장 종목 전체에 연산 처리가 가해지면서 비용 그래프가 선형으로 급증하여 월 비용 예측치가 $30를 가볍게 상회하는 문제가 발생했습니다. 파이프라인 내 각 레이어의 특성에 맞는 적절한 역할 분담이 강제되는 지점입니다.

### 두 번째 리스크: 서드파티 Search API의 요청 쿼리 한도 고갈

뉴스 소스 수집을 위해 Brave Search API를 백엔드로 채택했습니다. 개별 종목마다 목표주가 쿼리, 수주 현황, 일반 뉴스 등 3가지 갈래의 검색 요청을 전송하도록 코드를 작성했습니다.

그 결과 21개 종목에 종목당 3개 쿼리를 적용하면 일일 63건의 트래픽이 발생하며, 평일 21일 기준 월간 누적 요청 수는 1,323건으로 집계되었습니다. 이는 Brave Search 유료 스타터 플랜이 제공하는 월 1,000건의 무료 쿼리 한도를 한 달 반 만에 초과하는 구조적 결함이었습니다.

### 세 번째 리스크: 비공식 크롤러 라이브러리의 불확실성

주가 시계열 데이터를 래핑하는 오픈소스 라이브러리인 yfinance에 전적으로 의존했습니다. 비공식 야후 파이낸스 스크래핑 방식의 특성상 엔드포인트가 차단되거나 응답 객체의 데이터가 누락되는 이슈가 빈번했습니다. 특히 국내 증시 데이터 반영 속도가 느리거나 필드가 유실되는 현상이 잦아 상시 가동 인프라 환경에는 부적합하다는 결론을 내렸습니다.

## 4. 아키텍처 최적화 전략: 기획서 v3의 분산 구조

비용 리스크와 데이터 안정성 문제를 해결하기 위해 시스템 기획 및 아키텍처 설계를 총 세 번 리팩토링했습니다.

- **v1 모델:** 원본 텍스트 전체를 Claude Sonnet에 직접 파이프하는 구조 (일일 $2~3 비용 발생으로 폐기)
- **v2 모델:** 입력 토큰을 줄이기 위해 전처리 요약 레이어를 추가했으나, 요약 과정 자체에 AI 연산 리소스가 중복 소모되어 비용 수렴 실패
- **v3 모델:** 시스템 레이어별 역할 분산 라우팅 채택 (최종 채택)

### 기획서 v3 기반 아키텍처 제어 원칙

- Raw 데이터 수집 단계에서는 구글 RSS, 네이버 뉴스 등 비용이 발생하지 않는 무료 소스를 우선 가공합니다.
- 1차 전처리 및 노이즈 필터링은 비용이 들지 않는 규칙 기반 알고리즘(Rule-based Code)으로 전담 처리합니다.
- 2차 대량 종목 센티먼트 분류 작업은 경량화된 저비용 LLM 레이어에 위임합니다.
- 최종 맥락 분석 및 포트폴리오 정밀 진단 단계에만 Claude Sonnet의 컴퓨팅 파워를 집중 투입합니다.

## 5. 프로젝트 총평 및 기술적 의의

본 자작 주식 자동화 프로젝트를 운영하며 체감한 기술적 장단점입니다.

- **포지티브:** 장 시작 전 수작업으로 발생하던 리서치 리소스가 제로화되었으며, 정제된 코어 리포트가 스케줄러에 의해 지정된 시간에 카카오톡으로 정확히 딜리버리됩니다.
- **네거티브:** 가용 인프라 한도와 LLM 토큰 프라이싱 모델을 사전 계산하지 않을 경우 첫 런타임 가동부터 리소스 아웃이 발생할 수 있습니다. 상시 프로덕션 환경에서는 yfinance 같은 불안정한 래퍼 대신 공식 API 채널 확보가 필수적입니다.
- **필요 기술 스택:** 파이썬 중급 이상의 스크립팅 역량이 요구되며, 로컬 가상화 배포를 위한 Docker 컨테이너 기술 및 cron 데몬 제어 지식이 필요합니다. 로컬 NAS 장비가 없는 경우 별도의 클라우드 컴퓨팅 노드(EC2 등) 인프라 비용이 수반됩니다.

다음 2편 연재에서는 위에서 지적한 세 가지 병목 현상을 해결한 디테일한 백엔드 트러블슈팅 과정을 다룹니다. Claude Sonnet 독점 구조에서 구글 Gemini Flash-Lite 무료 티어로 엔진을 전환한 연동 가이드, KIS(한국투자증권) 공식 오픈 API 마이그레이션 과정, 그리고 소스를 5개 채널로 확장하면서도 API 오버헤드를 줄인 최적화 기법을 공유하겠습니다.
