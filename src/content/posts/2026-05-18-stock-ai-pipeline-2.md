로컬 서버 인프라 환경에서 AI 기반 주식 리포트 시스템을 2개월간 운용하며, 초기 아키텍처의 한계를 극복하고 월 고정 비용을 약 $6.5 수준으로 최적화하는 데 성공했습니다. 본 포스팅에서는 아키텍처 리팩토링 과정에서 직면했던 5가지 핵심 결함(Defect)의 원인 분석(RCA)과 구체적인 트러블슈팅 명세를 공유합니다.

---

## 1. 타겟 아키텍처 비용 명세

현재 리팩토링이 완료된 파이프라인은 평일 오전 8시 및 토요일 오전 10시 스케줄러에 의해 무인으로 구동되며, 고성능 모델과 경량 모델을 계층화하여 비용 효율성을 극대화했습니다.

### 컴포넌트별 리소스 요금 구조

- 보유 종목 심층 진단 엔진: Claude 3.5 Sonnet (인프라 핵심 연산) → 약 $1.4 / 월
- 장애 대응 폴백 레이어: Claude 3 Haiku (예외 처리 세션) → 약 $0.1 / 월
- 서드파티 검색 인프라: Brave Search API ($5 유료 플랜 적용) → $5.0 / 월
- 대량 종목 1차 스크리닝: Gemini 2.5 Flash-Lite → 무료 티어 적용 (0원)
- 시장 시계열 데이터 가공: KIS(한국투자증권) 오픈 API → 공식 채널 무료 제공 (0원)
- **월간 총 운용 비용: 약 $6.5 / 월**

---

## 2. 주요 트러블슈팅 및 리팩토링 명세

### 트러블슈팅 1: 컴퓨팅 자원 계층화(Tiering)를 통한 토큰 비용 제어

**현상 및 원인:** 초기 아키텍처에서는 3,000개 상장 종목 전체의 스크리닝 연산 레이어에 Claude Sonnet을 전면 배치하여 심각한 비용 오버헤드가 발생했습니다.

**해결 방안:** 연산의 복잡도에 따라 모델 레이어를 분할하는 디커플링 전략을 채택했습니다. 기술적 신호 감지는 규칙 기반 코드로 처리하고, 대량의 텍스트 기반 1차 센티먼트 필터링 및 2차 종목 쿼리는 무료 티어인 Gemini Flash-Lite 레이어로 위임했습니다. 최종 압축된 핵심 종목의 정밀 분석에만 Sonnet을 할당함으로써 컴퓨팅 단가를 극적으로 낮추었습니다.

**주의 사항:** Gemini 모델 도입 초기 프리뷰 에러(503 Service Unavailable)가 빈번히 관측되었으나, 정식 릴리즈 버전(`gemini-2.5-flash-lite`)으로 마이그레이션하여 런타임 안정성을 확보했습니다.

### 트러블슈팅 2: 환경변수 파싱 누락으로 인한 인증 실패 에러 (401 Unauthorized)

**현상 및 원인:** 5월 6일 배치 구동 중 판단 엔진 모듈에서 전체 종목 실패 로그(`error_code=999`)가 기록되었습니다. 디버깅 결과 401 인증 오류였으며, 원인은 설정 파일(`config.yaml`)에 치환 문자로 정의된 API Key 템플릿(`${GEMINI_API_KEY}`)이 실제 런타임 환경에서 주입되지 않은 채 텍스트 날것 그대로 서버로 전송된 것으로 확인되었습니다.

**해결 방안:** 최근 모듈 확장 과정에서 `engine.py` 내부에 `.env` 파일을 로드하는 파싱 로직이 유실된 멱등성 결함이었습니다. 수정 후 개별 모듈이 독자적으로 설정을 파싱하던 분산 구조를 폐기하고, 프로젝트 전체의 Configuration 인스턴스를 단일 엔드포인트에서 관리하는 공통 모듈로 통합했습니다.

### 트러블슈팅 3: 멱등성(Idempotency) 결여로 인한 재실행 비용 승수 효과

**현상 및 원인:** f-string 내 중괄호 문자열과 JSON 템플릿 리터럴이 충돌하는 구문 분석 오류(`ValueError`)로 인해 파이프라인이 강제 다운되었습니다. 이 시점에서 시스템을 수동 재시작할 때, 이미 Brave Search API 63건을 소모했음에도 불구하고 상태 저장(State Saving)이 되지 않아 중복 트래픽이 고스란히 재발생했습니다. 이로 인해 2주 만에 월간 할당량의 83%에 달하는 708건의 쿼리가 전출되는 리소스 유실이 있었습니다.

**해결 방안:** 세션 실패 시 처음부터 파이프라인을 재복구하는 구조적 결함을 보완하기 위해, 데이터 수집 레이어와 연산 레이어 사이에 캐싱 상태 변수를 도입하여 재실행 시 무조건적인 API 재호출을 방어하도록 로직을 수정했습니다.

### 트러블슈팅 4: 데이터 정합성 보장을 위한 KIS 공식 API 마이그레이션

**현상 및 원인:** 주가 시계열 래퍼 라이브러리인 yfinance 운용 중 국내 증시(.KS/.KQ) 마켓 코드 오분류, 장 마감 후 데이터 레이턴시(지연 변동), 크롤링 세션 차단 등의 프로덕션 이슈가 지속되었습니다. 중도 도입한 pykrx 역시 Docker 가상화 환경에서 빌드 종속성(Dependency) 분쟁을 유발했습니다.

**해결 방안:** 비공식 스크래핑 라이브러리를 전면 배제하고, 금융투자협회 표준 규격을 따르는 한국투자증권(KIS) 개발자 센터의 오픈 API로 정식 마이그레이션을 단행했습니다. 기관 공식 채널 활용을 통해 수급 데이터 및 공인 주가 정합성을 100% 신뢰 수준으로 끌어올렸습니다.

### 트러블슈팅 5: API 특이 프로토콜 대응 (주말 데이터 예외 처리)

**현상 및 원인:** KIS API 도입 후 첫 주말(토요일) 퀀트 스크리닝 배치 로깅 도중, 875개의 후보군 중 773개가 관리종목 코드로 오분류되어 대거 드롭되는 데이터 왜곡 현상이 나타났습니다.

**해결 방안:** API 응답 객체의 데이터 스키마를 확인한 결과, 관리종목 유무 필드(`mang_issu_cls_code`)가 개장 시간(평일)에는 `'0'` 또는 공백 문자열을 정상 반환하지만, 휴장 시간(주말)에는 서버 세션에 의해 `None` 객체로 반환되는 특이 동작 메커니즘을 발견했습니다. 파이썬 코드 레벨에서 `None` 데이터에 대한 널 가드(Null Guard) 예외 처리문을 한 줄 추가하여 정합성 버그를 픽스했습니다.

## 3. 결론 및 향후 아키텍처 고도화 방향

LLM 아키텍처 설계 시 단순히 API 연동에만 초점을 맞출 경우 토큰 프라이싱 모델의 한계와 데이터 공급망의 불안정성이라는 리스크를 직면하게 됩니다. 고성능 파이프라인 구축의 핵심은 코드 품질 자체보다 각 모듈의 명확한 경계 획정과 타이트한 예외 처리 설계에 있습니다.

현재 시스템은 안정화 단계에 접어들었으나 여전히 개선의 여지가 존재합니다. 이어지는 3편 포스팅에서는 데이터 소스 변천사 및 아키텍처 심층 분석을 다루며, KIS API 환경 내에서 자산을 효율적으로 파싱하고 멀티스레딩 데이터 처리를 구현하는 구체적인 백엔드 데이터 파이프라인 코드 구조를 분석하겠습니다.
