아이가 원하는 물건은 분명했다. 공부하다 모르는 걸 소리 내어 물어보면 답해주고, 문제집을 카메라로 찍으면 봐주고, 오늘 시간표나 일정을 알려주는 기기. 태블릿도 아니고 스마트 스피커도 아닌, 딱 그 세 가지만 하는 조용한 물건이었다.

![완성한 학습 파트너 기기 — 4.2인치 e-ink에 날짜·날씨·오늘의 영어·행운 팁을 띄운다](/images/2026-09-06-tech-001/img_00.jpg)

하드웨어는 금방 정해졌다. 카메라와 마이크가 보드에 내장된 [XIAO ESP32-S3 Sense](/posts/2026-08-03-tech-001)에 4.2인치 흑백 e-ink 패널, MAX98357A I2S 앰프와 작은 스피커를 붙였다. e-ink라 안 쓸 때는 화면을 그대로 켜둔 채 전력을 거의 먹지 않는다는 점이 학습기 용도에 잘 맞았다.

문제는 소프트웨어였다.

## 왜 샤오즈(Xiaozhi)로 시작했나

음성으로 대화하는 기기를 처음부터 만들려면 생각보다 많은 걸 직접 짜야 한다. 웨이크워드 감지, 마이크 오디오 캡처와 노이즈 처리, 음성을 텍스트로 바꾸고(STT) → AI에 넣고(LLM) → 다시 음성으로 만드는(TTS) 흐름, 그리고 이 오디오를 서버와 주고받는 통신 프로토콜까지.

샤오즈는 이걸 이미 다 구현해 둔 오픈소스 펌웨어다. 완제품이 아니라 뼈대라서, 원하는 보드(디스플레이·카메라 조합)에 대한 설정만 추가하면 내 하드웨어에서도 돌아간다. 처음부터 다 짜는 것보다 훨씬 빠를 것 같았다.

## 그런데 서버가 걸렸다

샤오즈로 대화를 하려면 서버가 필요하다. 선택지는 두 가지 — 공식 테스트 서버를 쓰거나, 오픈소스로 공개된 서버를 직접 호스팅하거나.

공식 서버는 편하지만 아이가 매일 하는 말이 어디로 가는지 알 수 없다. 오픈소스 서버를 직접 띄운다 해도 그 안에서 음성을 다시 남의 API로 넘기는 구조는 그대로다. 아이 음성 데이터가 내 손을 떠나는 게 마음에 걸렸다.

그래서 서버는 처음부터 직접 짜기로 했다. 펌웨어(샤오즈)는 그대로 두고, 서버 쪽 프로토콜만 내가 구현한 백엔드로 받는 방식이다. 백엔드는 [NAS](/posts/2026-08-06-tech-001)에 올려 24시간 돌리고, AI는 제미나이(Gemini)의 실시간 음성 API로 연결했다.

![학습기 ↔ NAS 백엔드 ↔ Gemini — 데이터가 집 안 네트워크 밖으로 나가지 않는다](/images/2026-09-06-tech-001/img_01.png)

이러면 데이터 경로가 전부 내 눈에 보이고, 나중에 카메라 확인이나 일정 조회 같은 기능도 남의 서버 구조에 맞출 필요 없이 내 코드에 바로 붙일 수 있다.

## 자작 백엔드에서 터진 버그 세 개

계획은 깔끔했는데, 막상 붙이니 오디오가 계속 이상하게 나왔다. 원인을 하나씩 잡는 데 며칠이 걸렸다.

**1. 소리가 깨지고 피치가 올라간다.** 서버가 기기에 접속 인사(hello) 메시지를 두 번 보내고 있었는데, 한 번은 샘플레이트를 16kHz, 다른 한 번은 24kHz로 알렸다. 펌웨어는 인사가 올 때마다 이 값을 아무 확인 없이 덮어썼고, 타이밍에 따라 16kHz가 최종적으로 남으면 실제 24kHz 스트림을 16kHz로 재생하니 소리가 빨라지고 깨졌다. 인사를 한 번만, 24kHz로 통일해서 해결.

**2. 두 번째 발화부터 AI가 못 알아듣는다.** 첫 질문은 잘 인식하는데, AI가 답을 하고 나면 그다음 말이 아예 감지되지 않았다. 원인은 에코였다. 이 기기에는 에코 캔슬러가 없어서 스피커로 나온 AI 목소리가 그대로 마이크로 다시 들어갔고, AI 쪽 음성 인식이 "침묵"을 영영 찾지 못해 말이 끝난 줄을 몰랐다. 브라우저는 마이크를 열 때 에코 제거를 기본으로 해주지만 ESP32 마이크는 맨몸이다. AI가 말하는 동안과 그 직후 잠깐, 서버에서 마이크 입력을 아예 버리는 방식으로 우회했다.

```python
# 서버: AI가 말하는 중 + 마지막 오디오 송신 후 1.2초는 마이크를 Gemini로 안 보낸다
MIC_GATE_TAIL_SEC = 1.2

def mic_is_gated(self) -> bool:
    return self.tts_active or time.monotonic() < self.mic_gate_until

async def send_mic_pcm(self, pcm16_bytes: bytes):
    if self.mic_is_gated():        # 게이트 걸렸으면 프레임을 그냥 버림
        return
    ...
```

**3. 재생 중에 소리가 겹쳐 들린다.** 제미나이는 응답 오디오를 실시간의 여섯 배 속도로 쏟아낸다. 15초 분량을 2초 만에 보내는 식이다. 서버가 이걸 그대로 기기로 넘기면 기기의 재생 버퍼가 넘쳐서 프레임이 겹쳐 재생됐다. 서버에서 앞부분만 몰아 보내 버퍼를 채운 뒤, 이후로는 실제 재생 속도에 맞춰 흘려보내도록 페이싱을 넣었다.

## 결국 샤오즈를 버렸다

세 버그를 다 잡고 나서도 마음이 편치 않았다. 샤오즈는 잘 만든 프레임워크지만 내 것이 아니다. 원하는 동작 하나를 바꾸려면 거대한 코드베이스에서 관련 부분을 발굴하듯 찾아야 했다. 한글 폰트가 화면에 안 나오는 문제 하나를 쫓는 데 세 시간을 썼을 때, 이 "고고학" 비용이 앞으로도 계속 나가겠다는 게 분명해졌다.

결정적인 건 따로 있었다. 샤오즈가 오디오를 Opus 코덱으로 압축해 주고받는 이유는 인터넷 대역폭 때문인데, 우리는 집 안 로컬 네트워크에서 제미나이 실시간 API에 연결한다. 이 API는 압축 없는 raw PCM 오디오를 그대로 받는다. 즉 Opus를 쓸 이유가 없고, Opus를 빼면 펌웨어에서 제일 까다로운 부분이 통째로 사라진다. 자체 펌웨어의 난이도가 생각보다 훨씬 낮아진다는 뜻이었다.

샤오즈 버전은 되돌릴 수 있게 git 태그와 바이너리로 백업해 두고, 아두이노로 펌웨어를 새로 썼다. 처음 시도가 실패했던 건 오디오 코덱 때문이 아니라 에코·음성 감지·웨이크워드·화면 갱신 네 가지였는데, 이번엔 그걸 설계 단계에서 명시적으로 처리했다. 웨이크워드는 포기하고 버튼을 누르면 대화가 시작되는 방식으로, 에코는 재생 중 마이크를 막는 2단 게이트로.

## 자체 펌웨어에서 또 삽질한 것

새 펌웨어에서도 출력 오디오에 "라디오 지지직" 같은 잡음이 남았다. 서버가 보낸 데이터를 주파수 분석해 보니 깨끗했고, 부팅 시 테스트 톤도 깨끗했다. WiFi 전파 간섭을 의심하며 한참 헤맸는데 그것도 아니었다.

진짜 원인은 재생 버퍼였다. 처음엔 서버가 보내는 오디오를 평범한 바이트 버퍼에 쌓았는데, 이 버퍼가 한 바퀴 돌아 시작 지점으로 되돌아올 때 오디오 프레임이 아무 위치(홀수 바이트 포함)에서 잘려 나갔다. 16비트 샘플 하나가 한 바이트씩 밀리면 그 뒤로 스트림 전체의 정렬이 어긋나고, 그게 지지직으로 들렸다.

해결은 프레임을 쪼개지 않고 통째로 보존하는 링버퍼(`RINGBUF_TYPE_NOSPLIT`)로 바꾸고, 버퍼를 PSRAM에 수십 초 분량으로 크게 잡는 것이었다. 제미나이가 응답을 실시간의 여섯 배 속도로 쏟아내니, 재생을 시작하는 시점엔 이미 한 턴 분량이 버퍼에 다 들어와 있어 WiFi가 잠깐 흔들려도 소리가 끊기지 않는다. 앞서 재생이 겹쳐 들리던 문제도 이 큰 버퍼로 같이 정리됐다.

```cpp
// 오디오 프레임(1920바이트)을 쪼개지 않고 통째로 저장·수신
spk_ring = xRingbufferCreateWithCaps(bytes, RINGBUF_TYPE_NOSPLIT, MALLOC_CAP_SPIRAM);

// MAX98357A 앰프는 32비트 프레임의 상위 16비트를 읽는다 → 16비트 샘플을 그 자리로 올린다
for (size_t i = 0; i < n; i++)
    scratch[i] = (int32_t)src[i] << 16;
```

여기서 한 번 더 헛다리를 짚었다. 나중에 "데이터가 16비트니까 I2S 슬롯도 16비트로 맞추면 깔끔하겠다" 싶어 16비트 스테레오로 바꿨더니 스피커가 거의 무음이 됐다. MAX98357A는 32비트 프레임의 상위 비트를 읽는 칩이라, 슬롯을 16비트로 줄이자 데이터가 하위 비트로 밀려 음량이 수만 배 줄어든 것이었다. 32비트 모노로 되돌렸다.

e-ink도 발목을 잡았다. 화면을 전부 다시 그리는 풀 리프레시가 1.7초쯤 걸리는데, 그동안 통신 버스를 독점해서 오디오가 끊기고 버튼이 씹혔다. 화면 전환을 풀 리프레시 대신 0.3초짜리 고속 부분 갱신으로 바꾸고, 대화 중에는 화면 갱신 자체를 미루도록 정리했다.

## 지금 되는 것

- **버튼 대화** — 버튼을 누르면 대화가 시작되고 다시 누르면 끝난다. AI에게는 초등 2학년 눈높이로 짧게, 그림·손가락 단계로 설명하라는 지침을 넣어 뒀다.
- **카메라 숙제 확인** — 문제집이나 손글씨를 찍으면 서버가 제미나이 비전 모델에 넘겨 봐주고, 힌트를 음성으로 돌려준다. 셔터는 버튼을 톡 누를 때만, 길게 누르면 화면 모드가 바뀐다.
- **e-ink 일정·시간표·날씨** — NAS 서버가 자정마다 그날 일정과 "하루 한마디 영어"를 기기에 밀어 넣는다. 날씨는 NAS가 한 번만 받아 여러 e-ink 기기에 공통으로 뿌리는 중앙 캐시에서 가져온다.
- **부모 메시지** — 부모가 폰이나 PC 웹페이지에서 한 줄을 입력하면 기기 가족 화면에 바로 뜬다.

## 케이스

케이스는 받침이 달린 전자잉크 인클로저 형태를 참고해 4.2인치 크기로 다시 그렸다. 화면을 앞으로 15도 눕힌 프레임 + 수평 베이스 + 후면 쐐기 받침 구조다. 스피커는 아이 쪽으로 소리가 나가도록 베이스 앞면에 그릴을 뚫어 배치했고, 카메라 커넥터가 처음부터 뒤를 향하도록 보드를 180도 돌려 넣어 FFC 케이블이 비틀리지 않게 했다.

![본체 STL — 15도 리클라인 프레임과 후면 받침, 위쪽 고양이 귀 장식](/images/2026-09-06-tech-001/img_04.png)

![베이스에 스피커를 앉힌 모습 — 앞면 그릴로 소리가 아이 쪽을 향한다](/images/2026-09-06-tech-001/img_02.jpg)

출력은 마쳤고 지금은 조립을 마무리하는 중이다. 카메라 FFC 고정과 개구부 마감이 남았다.

## 정리하며

오픈소스를 "가져다 커스텀"하려던 게 결국 서버도 펌웨어도 대부분 다시 짜는 일이 됐다. 그래도 음성 파이프라인을 어떻게 설계하는지에 대한 큰 그림은 샤오즈에서 배웠고, 무엇보다 아이가 하는 말이 우리 집 NAS 밖으로 나가지 않는다. 그 정도면 며칠어치 삽질값은 했다고 생각한다.
