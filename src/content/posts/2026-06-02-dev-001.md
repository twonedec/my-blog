매일 아침 정해진 시각, 텔레그램으로 메시지가 온다. 오늘 최저·최고 기온, 강수 확률, 현재 기온. 출근 일정이 있는 날엔 버스 도착 시각도 함께.

완성된 지금은 당연한 듯 쓰고 있지만, 여기까지 오는 데 예상보다 훨씬 많은 시행착오가 있었다.

## 이 글의 전제

아침 루틴이 문제였다. 날씨 앱 → 버스 앱 → 캘린더 앱, 세 개를 순서대로 열어야 출근 준비가 됐다. 어차피 아침에 텔레그램은 열게 되어 있으니, 이미 운영 중인 개인 봇에 날씨와 버스를 붙이면 됐다.

실제로 해보고 나서야 알았다. 공공 API가 이렇게 복잡한 줄은 몰랐다. 이 글은 구현 과정에서 직접 부딪힌 함정들을 정리한 기록이다.

## 기상청 API — 발표 시각마다 구조가 다르다

### 함정 1: 최저기온은 아침에 요청하면 없다

기상청 API는 날씨 데이터를 **발표 시각 기준으로 묶어서 제공**한다. 하루 여러 번 발표하고, 발표마다 포함된 예보 항목이 다르다.

아침 기준으로 최신 발표본을 가져오면 최저기온(TMN)이 없다. TMN은 **새벽 2시 발표에만** 당일 데이터가 포함된다. 처음엔 API 오류인 줄 알고 키 재발급까지 해봤다. 한참 뒤에야 발표 시각에 따라 항목 구성 자체가 달라진다는 걸 알았다.

**검증된 해결책:** 기온·강수 확률은 현재 기준 최신 발표본에서 가져오고, 최저기온만 새벽 2시 발표본에서 별도 요청한다. 요청이 두 번이 되지만 다른 방법이 없다.

### 함정 2: 발표 직후에 요청하면 데이터가 없다

발표 시각 직후에 API를 호출하면 아직 데이터가 없다. **발표 후 약 10분 뒤부터** 실제 데이터가 제공된다. 스펙 어딘가에 적혀 있긴 한데 처음엔 그냥 지나쳤다.

"방금 발표됐는데 왜 데이터가 없지?" 하고 디버깅하는 데 시간을 꽤 썼다. 발표 시각에서 10분 여유를 두고 최신 발표본을 선택하도록 로직을 수정했다.

### 함정 3: 어느 발표본이 "최신"인지 직접 계산해야 한다

기상청은 하루에도 여러 번 발표한다. 현재 시각 기준으로 가장 최근에 발표되었고, 이미 10분이 지난 발표본이 어느 것인지 직접 계산해야 한다. API가 "현재 최신 발표본을 주세요"라는 요청을 지원하지 않는다.

| 함정 | 원인 | 해결책 |
|------|------|--------|
| 최저기온(TMN) 없음 | 새벽 2시 발표에만 당일 TMN 포함 | 최저기온만 새벽 2시 발표본에서 별도 요청 |
| 발표 직후 데이터 없음 | 발표 후 10분 뒤부터 제공 | 발표 시각 + 10분 이후를 "유효 발표본"으로 간주 |
| 최신 발표본 판단 | API가 "최신 발표" 쿼리 미지원 | 현재 시각 기준으로 유효 발표 시각 직접 계산 |

## 버스 API — 서울과 경기도 체계가 다르다

버스는 날씨보다 더 복잡했다. API가 두 개인 것부터 시작이었다.

### 함정 4: 서울 버스와 경기도 버스는 API가 다르다

서울 버스는 서울시 공공 API, 경기도 버스는 경기도 버스 정보 시스템 API를 써야 한다. 같은 버스 정류장이라도 서울 지역과 경기도 지역이 다른 API를 쓴다.

처음에 서울시 API만 연동해서 정류장 정보를 조회했더니, 경기도 정류장 ID로는 결과가 아예 없었다. 정류장 ID 체계 자체가 다르다. 서울은 5자리 숫자, 경기도는 형식이 다르다. API 응답 구조도 달라서 파싱 코드를 두 벌 짜야 했다.

내가 타는 버스 노선이 경기도 영역이라 결국 경기도 버스 API를 따로 붙였다.

### 함정 5: 알람 예약이 중복 등록된다

봇 시작 시 출근 일정 체크 → 알람 예약, 매일 새벽 6시 체크 → 알람 예약, 두 경로가 있다. 같은 이름으로 등록하다 보니 봇을 재시작하면 동일한 알람이 두 번씩 울렸다.

**해결책:** 등록 전에 같은 이름의 알람이 이미 있으면 먼저 삭제하고 재등록. 어느 쪽 경로가 먼저 실행되든 항상 하나만 남는다.

### 함정 6: 재시작하면 예약 알람이 전부 사라진다

텔레그램 봇의 예약 알람은 메모리에만 존재한다. NAS가 재부팅되거나 봇이 어떤 이유로 재시작되면 예약해둔 알람이 전부 사라진다. 오후에 봇이 재시작되면 그날 퇴근 버스 알람은 조용히 없어진다.

**해결책:** 봇 시작 직후 캘린더에서 오늘 일정을 다시 읽어서, 현재 시각 이후인 알람만 골라 자동 재등록. "봇이 켜지면 오늘 남은 알람을 항상 복원한다"는 원칙을 코드로 구현했다.

| 버그 | 증상 | 해결 |
|------|------|------|
| API 미스매치 | 경기도 정류장 ID로 서울 API 조회 → 결과 없음 | 지역별 API 분기 처리 |
| 알람 중복 | 봇 재시작 후 같은 알람 2회 발송 | 등록 전 동일 이름 알람 삭제 후 재등록 |
| 알람 소멸 | 재시작 후 예약 알람 전부 사라짐 | 시작 시 미래 시각 알람 자동 재등록 |

## NAS 실행 환경 — 개발 환경과 실행 환경의 경로가 다르다

봇은 집 NAS(Synology)에서 돌아간다. 개발은 Mac에서 했다.

### 함정 7: Mac 마운트 경로로 NAS 실행 여부를 판단하면 안 된다

Mac에서 NAS 파일을 마운트하면 `/Volumes/home/` 경로로 접근한다. 봇 자체는 NAS 안에서 실행되므로 이 경로가 없다.

"NAS가 마운트되어 있는지 확인"하는 로직을 Mac 경로 기준으로 짜놨더니, NAS 안에서는 항상 "마운트 안 됨"으로 판단했다. 날씨·버스·캘린더 기능을 전부 건너뛰고 있었다. 한동안 왜 브리핑 메시지가 빈 채로 오는지 몰랐다.

**해결책:** NAS 고유 경로(`/volume1/` 존재 여부)로 실행 환경을 감지하고, 환경에 따라 파일 경로를 다르게 처리.

## 결론

매일 아침 날씨 메시지, 출근하는 날엔 버스 알람, 퇴근 시각엔 도착 예정 시간. 전부 텔레그램 하나로 들어온다. 앱 세 개 여는 루틴이 사라졌다.

공공 API 두 개(기상청, 버스)를 붙이는 게 별거 아닌 줄 알았다. 실제로는 일곱 개의 함정이 있었다. 특히 버스는 서울/경기 API가 다르다는 걸 처음부터 알았더라면 파싱 코드를 두 번 짜는 일은 없었을 것이다. 그리고 대부분의 버그는 "평상시엔 잘 되는데 재시작하면 안 된다"는 패턴이었다. 실제로 운영해보기 전엔 잘 안 보이는 종류다.
